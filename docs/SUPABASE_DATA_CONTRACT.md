## 3. Confirmed relationships and semantics

### Groups and memberships
- bandplan_groups.id is UUID primary key, generated by gen_random_uuid().
- name is required; normalized_name is generated from lower(trim(name)); name length is 3–50 characters.
- owner_id references auth.users(id) with ON DELETE CASCADE.
- Unique index exists on normalized_name.
- bandplan_group_members has group_id and user_id, both cascading foreign keys; composite primary key (group_id,user_id).
- Index exists on group_members.user_id.
- One user can belong to multiple groups.
- Membership list RPC returns group_id, group_name, owner_id, joined_at, role.
- Active group is stored in bandplan_user_state.state.activeGroupId.

### Shared state
- bandplan_group_state has group_id as primary key referencing groups(id) with cascade delete.
- state is JSONB, not null, default empty object.
- updated_at is timestamptz, not null, default now().
- RLS is enabled. Initial migration grants authenticated members select/insert/update and revokes delete.
- Realtime publication includes bandplan_group_state.

### Group data records
- Legacy client loads songs/events/setlists from each table's data JSON payload, filtered by active group_id.
- The JSON payload contains its own id; the table key is the composite group_id + id in the sync upsert behavior.
- Sync sends deltas, not full replacement snapshots, to avoid overwriting unrelated newer records.
- Deletes are explicit ID arrays in the sync RPC.

### Participation
- Valid statuses: yes, maybe, no; null/empty status clears the user's status.
- Participation is normalized in bandplan_event_participation and hydrated into event JSON for UI.
- Current RPC accepts event id, status, optional client timestamp, and optional group id.
- Server clamps client timestamps to a bounded window and applies last-write-wins.
- Participation changes are group-scoped and user-scoped.

### Personal state
- Personal songs and personal setlists are stored separately from group songs/setlists inside the user's state payload.
- Personal settings are also written to bandplan_accounts.personal_settings and merged with user state by the legacy client.
- Group-owned songs/events/setlists are not the same records as personalSongs/personalSetlists.

- Initial group migration enables RLS on bandplan_groups, bandplan_group_members, and bandplan_group_state.
- A private helper checks membership and is SECURITY DEFINER.
- Initial policies allow members to read their groups/memberships/shared state and insert/update shared state.
- A later hardening migration defines account ownership and group-member policies for songs, events, setlists, and invites.
- Profile directory access was tightened in 20261004204213_tighten_profile_directory_access.sql.
- This audit has not yet captured every policy expression or table grant. Do not consider the RLS review complete.

## 7. Offline contract observed in legacy browser client
- IndexedDB database name: bandplan-cloud-v1, schema version 3.
- Stores include snapshots, sync_queue, participation_queue, and event_offline_songs.
- Cache is scoped by account; pending sync and participation changes are durable.
- The Flutter app must implement platform-appropriate storage, not copy browser IndexedDB.
- Queue format, idempotency, retry, merge rules, and migration of existing offline-only changes need a separate design. Do not promise cross-device recovery of unsynced browser-local changes.

### Additional live security and Realtime verification

A second read-only catalog pass checked triggers, recycle-bin policies, Realtime publication membership, and function ACL/search_path settings.

**Triggers**

**Admin recycle bin**

- Treat it as server/admin-only. The Flutter client must not read or write this table. Do not add client policies as part of the migration without a separately reviewed product/security requirement.

**Realtime publication**
The live `supabase_realtime` publication contains:
- `bandplan_user_state`
- `bandplan_groups`
- `bandplan_group_members`
- `bandplan_group_state`
- `bandplan_accounts`
- `bandplan_songs`
- `bandplan_events`
- `bandplan_setlists`
- `bandplan_event_participation`
- `bandplan_state` (legacy locked table; do not subscribe to it in the new client).

No publication entry was returned for `bandplan_group_invites`, `bandplan_profiles`, `bandplan_friendships`, or `bandplan_admin_recycle_bin`. Realtime subscriptions should therefore be limited to the verified publication list and scoped with the user's authorized group/account identifiers.

**Live function ACL and search_path observations**
- Public business RPCs in the live catalog are SECURITY DEFINER and grant EXECUTE to `authenticated` and `service_role`; their configured search_path is pinned to `public, auth`.
- `bandplan_cleanup_expired_events()` and `bandplan_admin_table_info()` are SECURITY DEFINER but their ACL shows only `postgres` and `service_role`, not `authenticated`. Do not call them from the Flutter client.
- `bandplan_touch_updated_at()` is an ordinary trigger function, not SECURITY DEFINER.
- The recycle-bin policies query returned an empty array. This is an intentional client access boundary until proven otherwise.
- The catalog ACL string is evidence of current grants, not a recommendation to broaden them.

**Behavior confirmed in inspected live function definitions**
- `bandplan_join_group` locks the matching invite row, validates expiry/use limits, inserts a membership with conflict-do-nothing, increments invite uses only when a new membership is added, preserves existing memberships, updates account display name/roles only when non-empty values are supplied, and activates the joined group.
- `bandplan_leave_group` removes only the requested membership; if the departing user owns the group, ownership transfers to the earliest remaining member. If the owner is the sole member, the group is deleted. The user's active group is moved to another membership when possible; otherwise activeGroupId and group-bound arrays are cleared from their personal state.
- `bandplan_set_active_group` verifies membership before writing activeGroupId.
- `bandplan_set_event_participation` validates yes/maybe/no, verifies membership and event existence, clamps client timestamps, and applies last-write-wins per user/event/group.
- `bandplan_sync_group` upserts JSON records by group_id + id and processes explicit delete-ID arrays. When updating an event that contains participation, it merges the existing participation object with the incoming participation object rather than blindly replacing it.

**Migration implications**
- Preserve multi-group membership as a first-class relationship; never model a user as belonging to only one group.
- Group leave/delete must use the existing RPC semantics rather than direct table deletes.
- Keep event participation as a separate user-owned write path; do not let ordinary event JSON sync overwrite another member's participation.
- Keep account deletion, expired-event cleanup, admin metadata, and recycle-bin operations out of ordinary client code until their complete function bodies and authorization model are separately reviewed.
- No schema changes or production writes were made during this audit.


## 10. Legacy client payload contract — verified from current `bandplan.js`

The legacy browser app's top-level local state and group hydration were inspected directly. This section records only fields/semantics visible in the client; it is not a claim that every optional field is exhaustive.

### User state JSON

The client calls `saveUserState(userId, payload)` with:
- `activeGroupId`: UUID string or null.
- `profile`: `name`, `role`, `roles[]`, `defaultParticipation`.
- `settings`: user preferences object.
- `onboardingDone`: boolean.
- `personalSongs[]`: personal song records.
- `personalSetlists[]`: personal setlist/template records.

On group hydration, the client reads those same personal fields and overlays profile/settings with the account row. The personal library is not the group library.

### Group state JSON

The client hydrates `remote.state` into four top-level arrays:
- `songs[]`
- `events[]`
- `setlists[]`
- `members[]`

The app also stores the active group name as `profile.bandName` in its local view state. Member entries are expected to carry an account identity (the client matches `accountId` or `id` to auth user ID), display name, roles/role, color and optional note. A fallback current-member row is synthesized in the UI if no matching member is present in the roster snapshot.

### Song and chord representation

Verified song-level fields consumed by the UI include:
- `id`, `title`, `artist`, `key`, `lyrics`
- optional `fav`, `dynamics`, `tags`, and provenance fields used when copying between personal and group libraries (for example `groupSourceId`, `personalSourceId`, `addedAt`).

The current legacy chord representation is embedded in the `lyrics` text:
- inline chords use square-bracket tokens, e.g. `[Am]` within a lyric line;
- standalone chord rows are also supported;
- section headings use square brackets on a line by themselves, e.g. `[Куплет]`, and are distinguished from chord tokens;
- the client extracts chord tokens from both forms and transposes them in rendering rather than rewriting the stored lyric text.

**Flutter migration decision:** preserve the raw legacy `lyrics` string losslessly on import. Introduce a typed lyric document/anchor model only as a derived/editable representation with a reversible serializer. Do not split the text into guessed parallel arrays or discard whitespace/newlines; that would shift chord-to-word alignment and break existing songs. Keep section markers distinct from chord anchors.

### Events and participation

Group events are hydrated as JSON objects from `group.events[]`. The client overlays `myStatus` using the normalized participation map returned separately by the cloud adapter, with fallback to `event.participation[authUserId]` or legacy `event.myStatus`. This confirms that:
- `myStatus` is a client-side convenience field, not the normalized database key;
- normalized participation belongs to `bandplan_event_participation`;
- event JSON may still contain legacy participation snapshots and must be read compatibly during migration.

### Setlists and cross-library references

- Setlists are group JSON records in `group.setlists[]`; personal templates are in `user_state.state.personalSetlists[]`.
- Setlist items reference songs by `songId`.
- Template conversion copies referenced songs into the personal library and rewrites item references to the personal song IDs.
- Importing a personal template into a group copies songs into the group library and rewrites item references to group song IDs.
- The client intentionally makes these copies independent; it does not maintain a live cross-scope song reference.

### Settings and defaults visible in the legacy client

The legacy defaults include:
- theme: `light`
- accent: `#2547D0`
- notation: `auto`
- weekStart: `1`
- lyricsSize: `15`
- sceneSize: `26`
- sceneSpeed: `60`
- autoscroll: `true`
- reduced: `false`
- calView: `month`
- toastMode: `off`
- showChords: `true`

These are migration defaults, not a mandate to retain the old visual design. The new app's preferred accent/design system can differ, but user-imported settings should be mapped deliberately and unknown keys should not be silently dropped during compatibility reads.

### Important compatibility rules for Flutter

1. Preserve unknown JSON keys when round-tripping legacy song/event/setlist records until a typed migration has proven they are obsolete.
2. Keep personal and group collections separate in the domain and repository layers.
3. Treat all imported IDs as opaque identifiers; do not regenerate them on ordinary reads.
4. Preserve raw lyrics exactly, including spaces and line endings, until the chord-anchor editor can serialize without loss.
5. Resolve setlist item `songId` references within the same scope first (group-to-group or personal-to-personal).
6. Keep normalized event participation as an independent repository operation.
7. Treat roster snapshots as presentation/cache data; authoritative membership is `bandplan_group_members` and the group-list RPC.


## 11. Final RPC behavior and security-advisor findings

The remaining live function definitions were inspected read-only.

### Group creation and invite behavior

- `bandplan_create_group(p_name, p_display_name, p_roles)` requires an authenticated user, validates a 3–50 character group name, creates the group and membership, upserts account display name/roles without overwriting non-empty values with empty inputs, generates a 10-character uppercase hex invite code, initializes group state with empty `members/events/songs/setlists` arrays, and activates the group.
- `bandplan_create_group_and_invite(..., p_group_id)` either validates membership in the supplied group or selects the user's active/earliest membership. If no group exists, it creates one (using the supplied name or fallback `Моя группа`). It returns an existing valid invite created by the current user or creates a new unlimited-use invite, then activates that group.
- `bandplan_get_invite_code()` is not a pure read: if the user has no group, it creates a group using their account display name/roles, then creates or returns an invite code. The Flutter UI must make this side effect explicit and must not call it merely to preview invite availability.
- `bandplan_delete_my_account()` is destructive and deletes the authenticated row from `auth.users`. Before doing so, it transfers ownership of owned groups to the earliest remaining member, deletes groups with no remaining members and their group data, reassigns shared record `updated_by` values, removes participation/friendship/member/invite/account/profile/user-state references, and deletes the auth user. This operation requires a clearly confirmed user flow and must never be called as a background cleanup.
- `bandplan_cleanup_expired_events()` deletes expired one-off events and repeating series only when their explicit `repeatUntil` date has passed; it also removes corresponding participation rows. It is a server/admin maintenance operation, not a mobile-client operation.
- `bandplan_admin_table_info()` returns public table metadata excluding the recycle bin. It is administrative metadata and not part of the app client contract.

### Security advisor snapshot (2026-10-31)

The Supabase security advisor returned:
- INFO: `bandplan_admin_recycle_bin` has RLS enabled but no policies. This is an intentional closed client boundary; do not add a permissive policy to silence the lint.
- WARN: 12 authenticated-callable SECURITY DEFINER RPCs. The advisor flags the pattern generically; several are required business operations and explicitly verify `auth.uid()` and/or group membership. Each function must continue to be reviewed individually for authorization, pinned search_path, and safe inputs. Do not revoke all EXECUTE grants indiscriminately because that would break the current client contract.
- WARN: leaked-password protection is disabled in Supabase Auth. This is a dashboard-level security setting; it was not changed during this repository task. The project owner should review enabling it after checking expected sign-up behavior.
- The advisor snapshot is time-bound and should be re-run before production release.

- Android app link/custom scheme callback registration and package SHA fingerprints where applicable;
- iOS bundle ID and universal-link/custom-scheme callback registration;
- Google provider enabled state, client IDs, and authorized redirect URI;
- Apple provider enabled state, Services ID / bundle association, and key configuration.

Do not copy secrets into the repository. Store only non-secret public client identifiers in platform configuration and keep provider secrets in Supabase Auth settings. Until these values are verified, OAuth must be treated as not yet configured for native builds.


## 12. Live write-permission correction (2026-11-02)

A live catalog check found that `authenticated` had SELECT privileges on
`bandplan_songs`, `bandplan_events`, and `bandplan_setlists`, but did not
have INSERT, UPDATE, or DELETE privileges. The corresponding member-only RLS
policies already existed, so client upserts and deletes were rejected before
those policies could authorize a row.

The missing table privileges were granted to `authenticated` for these three
tables only. RLS remains enabled and the existing membership policies remain
the row-level authorization boundary. A follow-up query verified SELECT,
INSERT, UPDATE, and DELETE privileges are all present while RLS is enabled.

The Flutter repositories now request the saved row after each upsert
(`.select('id').single()`) and verify delete results. This makes a rejected or
empty write surface as an error instead of allowing the editor to close as if
the operation succeeded. The song, event, and setlist screens already
invalidate their respective Riverpod providers after successful writes, so
the updated records are reloaded into the UI.

The group RPCs were separately checked in the live catalog: create, join,
leave, active-group selection, and group-list RPCs are executable by
`authenticated`; they are SECURITY DEFINER functions with server-side
membership/authentication checks. The Flutter group repository now validates
that create, join, and leave RPCs return a group identifier, and validates the
active-group selection result before treating the action as successful.

No table structure, RLS policy, authentication flow, or RPC definition was
changed by the write-permission correction.


## 13. Group RPC ambiguity fix (2026-11-02)

The live PostgreSQL functions were failing before completing group actions.
Because `bandplan_create_group` returns an OUT column named `invite_code`,
its unqualified `where invite_code = v_code` lookup conflicted with the
PL/pgSQL output variable. Likewise, `bandplan_leave_group` returns an OUT
column named `group_id`, and unqualified membership-table references to
`group_id` were ambiguous.

The functions were replaced with equivalent implementations that qualify
table columns through aliases. Existing authorization checks, SECURITY DEFINER
ownership, pinned search_path, membership behavior, invite generation,
ownership transfer, and last-owner cleanup were retained. No table, column,
RLS policy, or authentication flow was changed.

A live database transaction exercised group creation, invite-code return,
joining by that code, a member leaving, and the sole owner leaving. It completed
without SQL errors and was rolled back, so the diagnostic group and membership
rows were not retained. The migration is tracked in
`supabase/migrations/20261102190000_fix_group_rpc_ambiguous_column_references.sql`.
